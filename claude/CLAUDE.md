# CLAUDE.md

## 確認と停止

次の場合は作業を停止し確認を求める。

- 設計など影響範囲が大きい変更 (大規模リファクタリングを含む)
- 仕様変更が必要
- セキュリティへ影響する変更

要件が曖昧な場合は複数案を推奨とともに提示する。

## 調査

- 表面的な対症療法ではなく根本原因の解決を優先する
- 憶測で修正せず、ログ・エラーメッセージ・関連コードを確認して原因を調査してから対応する
- 再現可能な問題は再現手順を確認してから対応する

## 実装

- 要求された作業の範囲内で実装し、無関係な変更は行わない
- 必要以上に抽象化せず、今必要な機能だけを実装する
- エラーを握りつぶさない
- 実装とドキュメントは可能な限り同期する

## 何をどこに書くか

コードには How、テストコードには What、コミットログには Why、コードコメントには Why not を書く。

- テストコード: テスト名と構成で「何を保証するか (仕様)」が読めるようにする
- コミットログ: 件名で変更内容が分かるようにし、本文に変更した理由を書く
- コードコメント: 素直な書き方を選ばなかった理由と、コードから読み取れない制約 (順序の依存・外部の不具合への対処など) だけを書く。何をしているかの説明は書かない

TODO / FIXME は依頼がない限り書かない。やり残しは報告の「懸念事項」で伝える。

例外:

- 公開 API のドキュメントコメントは言語の慣習に従う
- 設定ファイルでは、キー名や値から意味が読み取れない設定に限り、何を設定しているかを書いてよい

## Git

- 1 コミット 1 目的。機能追加・リファクタリング・フォーマット変更は分ける
- Conventional Commits を使用する。ただし、リポジトリの規約や直近の履歴が別の形式ならそちらに従う
- git worktree を使う場合、既存の worktree 内でブランチを切り替えない。新しい作業には新しい worktree を作成する (既存 worktree 内で切り替えると、その worktree が元ブランチの最新化役を果たせなくなり、ローカルのブランチ参照が origin から静かに乖離する)

## 完了時

コードや設定を変更した作業では、完了とする前に次を行う。

- プロジェクトに用意されている Build・Test・型チェック・Lint・Format を実行する。Format と Lint の自動修正は変更したファイルだけにかける
- UI/フロントエンドの変更は実際に動作確認する

完了したら、次の形式で簡潔に報告する。質問への回答や議論には付けない。

- 実施内容
- 影響範囲
- 実施した確認
- 未実施の確認
- 懸念事項
